# Preferências do Igor (igorSeberino)

Gosto geral dele, tirado de projetos anteriores. Vale como ponto de partida, **não como
receita**: cada projeto tem tema, público e conteúdo próprios. Se o pedido atual contradiz
algo daqui, o pedido atual ganha.

## Como ele trabalha

- pt-BR informal e direto. Quer o agente executando até o fim, sem confirmar cada passo.
- Corrige com dados concretos (print, arquivo, link) e espera que a correção seja conferida
  na fonte antes de aceitar ou rejeitar.
- Commits em Conventional Commits simples (`feat:`, `fix:`, `docs:`, `chore:`, `test:`, `ci:`).
- Revisão de docs = auditar contra o código e já abrir o PR com as correções. Só as decisões
  de configuração ou acesso ficam com ele.

## Gosto visual (perfil ou pedido explícito de visual)

- **O tema muda a cada projeto.** Nunca reaproveite tema, paleta, motivo ou copy de um
  trabalho anterior sem ele pedir. Derive do assunto atual ou pergunte no `clarify`.
- Gosta de tema assumido e bem executado, não de enfeite tímido. Se o tema existe, ele aparece
  no conjunto inteiro, não num banner isolado.
- Coerência acima de tudo: uma seção crua (tabela, `##`, selo padrão) no meio de seções
  estilizadas incomoda. Se uma seção destoa, refaça o visual dela no mesmo padrão.
- Movimento sutil. Objeto cruzando a tela já foi vetado; evite por padrão.
- Copy natural. Frase de efeito forçada e trocadilho explicado são vetados. Humor só se vier
  dele ou de um fato real dele, e no máximo um toque recorrente.
- Sem disclaimer, aviso ou rodapé que ninguém pediu.

## Como receber feedback

- "Melhorar" uma seção não é removê-la: manter o conteúdo e refazer o visual.
- Quando ele veta um elemento, tire **só** aquele elemento. Não reinterprete o resto.

## Repo de projeto

- README convencional e explicativo, em markdown. O estilo pessoal do perfil não entra.
- Em trabalho de grupo, se existir um repo de referência do grupo, siga o modelo dele
  (estrutura do README, padrão de nome do repo). Sem código de disciplina ou de avaliação
  no nome do repo.

## Fatos

Não guarde nem reuse fatos de projeto anterior (cargo, formação, contatos, projetos). Eles
envelhecem. Rode a auditoria e confirme no `clarify` toda vez.
